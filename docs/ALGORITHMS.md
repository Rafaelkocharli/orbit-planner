# Алгоритмы планирования

Три планировщика, выбираются при создании смены или ветви. Все видят только текущее состояние,
известный план и полученные сообщения; действия исполняет библиотека организаторов.

| Имя | Идея | Время на смену* | Когда использовать |
|---|---|---|---|
| `cpsat-mpc` | точное расписание на 3 часа вперёд (CP-SAT), пересчёт каждый час и после событий | P02 ≈ 20 с, P03 ≈ 2 мин, P04 ≈ 35 с (сервер: 68 с, 6,5 мин, 92 с) | основной режим, максимальный результат |
| `reserve` (по умолчанию) | резервирование «всё или ничего» по приоритету и ценности | 1–10 с | режим по умолчанию: секунды на смену; стартовое решение для `cpsat-mpc` |
| `greedy-edf` | ближайший срок / приоритет на каждом шаге | < 1 с | простое правило для сравнения |

\* один поток решателя; ноутбук Apple M, в скобках — сервер 1 vCPU.

## Общие решения

**Задание выполняется целиком или не начинается.** Частичная работа выручки не приносит, поэтому
новые планировщики берут задание, только если вся оставшаяся работа помещается в окно. Простое
правило тратило на невыполненные задания до 444 шагов работы; новые — ноль.

**Энергия — гарантированная нижняя оценка реального заряда.** Используется тот же переход, что в
модели, `E' = min(C, E + min(ηc·b, b/ηd)·dt)`, где `b` — солнечная мощность минус нагрузка, но:
- нагреватель и окно зарядки берутся из прогноза температуры при **ожидании** — это самая холодная
  траектория (любое действие добавляет нагрузку и поднимает температуру), поэтому нагреватель
  прогнозируется не реже, а зарядка не чаще, чем в реальности;
- округление консервативное: базовый баланс вниз, мощность действия вверх (единица 0,01 Вт·ч).

По индукции реальный заряд не ниже оценки, поэтому действие, допустимое по оценке (заряд не ниже
резерва в начале и конце шага), допустимо и в модели. Тест `test_energy_model_is_a_lower_bound`
проверяет это на исполненных траекториях. Итог: ни одной отклонённой команды во всех прогонах.

**Температура.** Во всех данных она остаётся в диапазоне 4–36 °C при допуске −5…45 °C, поэтому
ограничение проверяется, но на выбор не влияет.

## `reserve` — резервирование

На каждом пересчёте (каждые 12 шагов, после события или смены цели, при отклонении от плана):

1. Для каждого незавершённого задания — допустимые клетки «аппарат × шаг» в окне: исполнитель,
   контакт, доступность. Считается ожидаемый спрос на каждую клетку.
2. Калибровки ставятся перед истечением текущей, в наименее востребованный шаг.
3. Задания перебираются по порядку: начатые → (цель «приоритет») приоритет 3, затем ценность
   за шаг работы / (цель «выручка») ценность за шаг, затем приоритет 3 → меньше вариантов → раньше срок.
4. Задание принимается, только если **вся** оставшаяся работа помещается: свободные клетки,
   лимит каналов, действующая калибровка, заряд по оценке выше резерва. Клетки берутся с
   наименьшим спросом, чтобы гибкие задания оставляли дефицитные окна тем, кому они нужнее.

Плюсы: быстро, объяснимо, в P02–P04 выполняет все выполнимые задания приоритета 3.
Минусы: решение по заданию не пересматривается внутри пересчёта — до оптимума не всегда доходит
(P03: 97,5% заданий).

## `cpsat-mpc` — оптимизация на скользящем горизонте

На каждом пересчёте решается задача на `H = 36` шагов (3 часа) всеми ограничениями сразу:

- переменные: `x[j,s,t]` — аппарат `s` работает над заданием `j` на шаге `t` (только допустимые
  клетки); `c[s,t]` — калибровка; `E[s,t]` — оценка заряда;
- одно действие на аппарат и шаг, один исполнитель на задание и шаг, не больше
  `downlink_parallel_limit` передач на Землю за шаг;
- работа разрешена при действующей калибровке: возраст ещё мал или калибровка за последние
  `calibration_valid_steps` шагов; пока горизонт короче срока действия, аппарату нужна максимум
  одна калибровка;
- заряд — нижняя оценка (см. выше), действие требует резерва в начале и конце шага;
- задание со сроком внутри горизонта: `Σx = остаток · z_j` (целиком или никак);
- цель (лексикографически через веса): «приоритет» — задания приоритета 3 ≫ выручка;
  «выручка» — выручка ≫ приоритет 3; затем частичный прогресс по заданиям за горизонтом, запас
  заряда в конце горизонта, более ранняя работа (оставляет место срочным заявкам), меньше калибровок.

Решатель: OR-Tools CP-SAT, один поток, фиксированное зерно, **детерминированный** лимит времени
(`time_limit` = 3 единицы), полная LP-релаксация (`linearization_level = 2`), остановка при
доказанном разрыве меньше $1. На одной платформе одинаковый вход — одинаковое расписание (между
разными процессорами возможны расхождения на единицы заданий).

Надёжность:
- стартовое решение — план `reserve` на тот же горизонт; он допустим в модели точно (общая
  целочисленная арифметика энергии, проверяется тестом), поэтому решатель начинает с хорошего плана;
- после решения исполняется лучший из двух планов по весам цели — решение с лимитом времени
  никогда не хуже резервирования;
- если модель больше `max_variables` (перегрузка P04: ~24 000 переменных), точное решение не
  укладывается в бюджет на одном ядре — используется резервирование на весь остаток смены.
  Журнал пересчётов показывает это честно (`status = RESERVATION`).

Параметры (`params` при создании запуска):

| Параметр | По умолчанию | Смысл |
|---|---|---|
| `horizon` | 36 | горизонт, шагов |
| `replan_every` | 12 | плановый пересчёт, шагов (плюс после событий и отклонений) |
| `time_limit` | 3.0 | детерминированный лимит решателя на пересчёт |
| `terminal_soc_pct` | 55 | желаемый заряд в конце горизонта, % |
| `partial_credit` | 0.8 | доля ценности за прогресс по заданиям, которые кончаются за горизонтом |
| `max_variables` | 15000 | выше — план резервирования |
| `max_candidates` | 0 | отсев кандидатов на клетку (0 — без отсева) |
| `energy_margin_wh` | 0.3 | запас над резервом, Вт·ч |
| `seed` | 0 | зерно решателя |

Подбор: горизонт 48 с пересчётом каждые 8 шагов давал худший результат на P03 (решатель не
успевал), 36/18 — чуть хуже 36/12; лимит 1–1,5 заметно снижал качество на P03. Значения по
умолчанию — лучшие из проверенных.

Журнал: `GET /api/runs/{id}/planner` и карточка «Как работал алгоритм» на вкладке «Обзор» —
причина каждого пересчёта (начало, плановый, сообщение, смена цели, отклонение), статус
(оптимум доказан / допустимое решение / резервирование), число заданий и разрыв с границей.

## `greedy-edf` — простое правило

На каждом шаге: калибровка за шаг до истечения; затем открытые задания, которые ещё успевают,
по порядку «приоритет → срок → ценность» (цель «приоритет») или «срок → ценность за шаг»
(цель «выручка»); каждому — первый свободный допустимый аппарат. Лимит каналов и одного
исполнителя соблюдается самим правилом. Вперёд не смотрит.

## Верхние границы

`python -m experiments.upper_bound` решает LP-релаксацию всей смены (OR-Tools GLOP): те же
ограничения назначений, калибровка снята, задание засчитывается пропорционально работе, энергия
в оптимистичной форме — нагреватель выключен, зарядка всегда разрешена, без округлений. Ослабление
ограничений только поднимает оптимум, поэтому значение — доказанный потолок для любого алгоритма
(для запусков без нехватки питания: обнуление заряда снизу не моделируется). Считаются четыре
потолка: число заданий, задания приоритета 3, выручка, выручка при максимуме приоритета 3.

Задание засчитывается **невыполнимым**, если в его окне меньше шагов со связью у допустимых и
доступных аппаратов, чем нужно работы. Это проверяемое основание: сервис показывает окно и
список пригодных шагов.
