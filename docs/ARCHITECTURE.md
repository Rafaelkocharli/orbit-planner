# Архитектура

## Компоненты

```
 браузер (React)  ──HTTP /api──►  FastAPI (backend/app/main.py)
                                   │
                                   ├── runs.py       запуски: Session организаторов + планировщик + история
                                   ├── storage.py    файлы: сценарии по хэшу, запуски = сообщения + команды
                                   ├── scenarios.py  каталог сценариев, изменение условий, сохранённые варианты
                                   ├── planners/     cpsat-mpc, reserve, greedy-edf
                                   ├── analysis.py   причины потерь, доказательство невыполнимости, разбор решения
                                   ├── whatif.py     прогноз, сравнение, ветви стратегий, «что если»
                                   ├── report.py     читаемый HTML-отчёт
                                   └── tasks.py      фоновые задачи с прогрессом
                                   │
                                   ▼
                          model/  (библиотека организаторов, без изменений)
                          Session: observation / apply_event / advance / fork / result
```

Расчёт физики и учёта — только библиотекой организаторов `model/`: энергия, температура, допуск
действий, прогресс, выручка и сводка считаются там. Наш код выбирает действия и анализирует
историю, но не пересчитывает состояние по своим правилам. Поэтому выгрузка любого запуска
воспроизводится утилитой `model/operations.py`.

| Слой | Файлы | Отвечает за |
|---|---|---|
| Данные и модель | `model/`, `data/` | формат сценария, правила перехода, учёт |
| Планирование | `backend/app/planners/` | выбор действий на шаг; видит только текущее состояние и полученные сообщения |
| Запуски | `runs.py`, `storage.py`, `tasks.py` | жизненный цикл смены, ветви, сохранение, фоновые расчёты |
| Анализ | `analysis.py`, `whatif.py`, `report.py` | объяснения, прогнозы, сравнение, отчёт |
| API | `main.py` | HTTP, проверка ввода, изоляция клиентов, блокировки |
| Интерфейс | `frontend/src/` | экран оператора; каждая вкладка — отдельный компонент |
| Эксперименты | `experiments/` | воспроизводимые прогоны, верхние границы, стресс-проверка |

## Жизненный цикл запуска

1. `POST /api/runs` — сценарий (встроенный, сохранённый или загруженный) проверяется
   `validate()` организаторов; изменённые условия создают новый сценарий с шага 0.
2. `POST /api/runs/{id}/events` — сообщение применяется на текущем шаге до выбора действий
   (`Session.apply_event`). Некорректное или повторное отклоняется целиком, состояние не меняется.
3. `POST /api/runs/{id}/advance` — на каждом шаге планировщик выбирает действия, `Session.advance`
   исполняет их. Долгий расчёт идёт фоновой задачей со статусом и прогрессом.
4. `POST /api/runs/{id}/fork` — независимая ветвь: копия среды, истории и внутреннего состояния
   планировщика. Цель можно сменить на границе шага, смена пишется в историю.
5. `GET /api/runs/{id}/result` — выгрузка `cosmo-B-ops-result-1.0`: исходный сценарий, сообщения
   в порядке получения, команды, число шагов, сводка, `run_metadata` (цель, алгоритм, версия,
   параметры, смены цели, точка ветвления).

## Гарантии

- **Временная корректность.** Будущие сообщения нигде не хранятся: планировщик и прогнозы
  используют только полученное. Выполненные шаги не пересчитываются.
- **Изоляция.** Клиент передаёт `X-Client-Id`; интерфейс создаёт его один раз и хранит в браузере.
  Запуски и сохранённые сценарии разных клиентов не видны друг другу.
- **Сохранность.** Каждое изменение запуска пишется на диск: сценарий по SHA-256, сообщения,
  команды. После перезапуска сервиса запуск восстанавливается повторением команд — состояние
  пересчитывается, а не читается из файла.
- **Блокировки.** Пока идёт фоновый расчёт, запуск отвечает `409` на изменения; чтение ждёт.
- **Прогнозы и «что если» не меняют запуск** — они работают на копиях.
- **Один процесс API.** Запуски и блокировки живут в памяти процесса, поэтому uvicorn работает с
  одним воркером; тяжёлые расчёты идут в пуле фоновых задач.

## Причины невыполнения

Причина отказа команды (факт одного шага) и причина срыва задания разделены. Для просроченного
задания перебираются все шаги окна, где у допустимого аппарата был контакт, и для каждого
определяется, что помешало; допустимость по энергии и температуре пересчитывается по правилам модели.

| Причина | Смысл |
|---|---|
| `infeasible_contacts` | доказуемо: шагов со связью в окне меньше, чем работы — неустранимо при любых действиях |
| `busy_other_job` | допустимые аппараты работали над другими заданиями |
| `ground_capacity` | оба канала связи с Землёй заняты |
| `calibration_expired` / `calibrating` | калибровка истекла / шла в шаг связи |
| `energy_reserve` / `thermal_limit` | действие нарушило бы резерв заряда / температурный диапазон |
| `satellite_unavailable` | аппарат недоступен |
| `not_scheduled` | условия позволяли, планировщик выбрал другое — недостаток алгоритма |

## API

Полная схема — `/docs` (OpenAPI). Тяжёлые операции принимают `"background": true` и возвращают
задачу (`202`); статус и результат — `GET /api/tasks/{id}`.

### Сценарии

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/api/meta` | цели, планировщики, типы сообщений, ключи изменений, сценарии |
| GET | `/api/scenarios` | встроенные и сохранённые сценарии |
| GET | `/api/scenarios/{id}` | состав группировки, модель, задания; `?full=true` — весь JSON |
| POST | `/api/scenarios` | загрузить сценарий (`scenario`) или сохранить вариант (`base_id` + `overrides`, `title`) |

`overrides`: `initial_soc` `{sid или "*": pct}`, `solar_factor`, `job_priority` `{job_id: 1..3}`,
`failures` `[{satellite_id, start_step, end_step}]`, `downlink_parallel_limit`.

### Запуски

| Метод | Путь | Назначение |
|---|---|---|
| POST | `/api/runs` | новый запуск: `scenario_id` или `scenario`, `overrides`, `goal`, `planner`, `params`, `label` |
| POST | `/api/runs/import` | загрузить выгрузку `cosmo-B-ops-result-1.0`, восстановить и продолжить |
| GET | `/api/runs` | мои запуски |
| GET / DELETE | `/api/runs/{id}` | состояние (шаг, сводка, аппараты, сообщения) / удалить |
| POST | `/api/runs/{id}/advance` | `{"steps": n}`, `{"until_step": k}` или `{}` до конца; `background` |
| POST | `/api/runs/{id}/events` | одно сообщение; без `id`/`at_step` они заполняются (ручной ввод) |
| POST | `/api/runs/{id}/goal` | смена цели на границе шага |
| POST | `/api/runs/{id}/fork` | ветвь из текущего состояния: `goal`, `planner`, `params`, `label` |

### Просмотр и анализ

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/api/runs/{id}/jobs` | задания: прогресс, статус, исполнители; фильтры `status`, `priority`, `kind`, `satellite_id` |
| GET | `/api/runs/{id}/schedule` | исполненное расписание по аппаратам (диаграмма Ганта) |

| GET | `/api/runs/{id}/analytics` | по приоритетам, загрузка, периоды дефицита, отклонённые команды, причины невыполнения |
| GET | `/api/runs/{id}/missed` | все просроченные задания с причиной и разбивкой |
| GET | `/api/runs/{id}/jobs/{job_id}/why` | почему задание не выполнено; доказательство невыполнимости |

| GET | `/api/runs/{id}/result` | выгрузка `cosmo-B-ops-result-1.0` |
| GET | `/api/runs/{id}/report` | читаемый HTML-отчёт |

## Как добавить планировщик

Класс с `name`, `version`, `params()` и `plan(session, goal) -> {satellite_id: action}` в
`backend/app/planners/`, строка в `PLANNERS` (`planners/__init__.py`). После этого он появляется
в интерфейсе, в ветвях стратегий, экспериментах и `run_metadata`. Экземпляр копируется при
ветвлении; после восстановления с диска создаётся заново и может восстановить внутреннее
состояние в необязательном `restore(session)`.
