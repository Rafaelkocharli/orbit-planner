# Orbit Planner

Веб-сервис автономного управления спутниковой группировкой — КосмоХакатон 2026.

Оператор смены загружает сценарий, выбирает цель (приоритетное обслуживание или коммерческая
отдача) и запускает расчёт. Сервис сам распределяет задания между аппаратами с учётом энергии,
калибровки, окон связи и сроков, принимает новые сообщения по ходу смены, перестраивает план,
объясняет решения и потери, сравнивает варианты и сохраняет воспроизводимый результат.

**Сервис:** http://185.249.152.10 · **API:** http://185.249.152.10/docs

## Запуск

Нужны Python 3.10+ и Node.js 20+.

```bash
make install     # виртуальное окружение Python + npm install
make serve       # собрать интерфейс и запустить сервис → http://localhost:8000
```

Для разработки — два процесса: `make dev-api` (API на :8000) и `make dev-ui` (интерфейс на :5173
с проксированием `/api`). Тесты: `make test`.

Docker:

```bash
docker build -t orbit-planner .
docker run -p 8000:8000 -v orbit-storage:/app/storage orbit-planner
```

Переменные окружения: `ORBIT_STORAGE_DIR` — хранилище запусков (по умолчанию `storage/`),
`ORBIT_MAX_RUNS` — запусков в памяти, `ORBIT_TASK_WORKERS` — потоков фоновых задач.
Внешние сервисы, ключи и платные подписки не нужны.

## Работа оператора

1. **Сценарий.** На стартовом экране выбрать сценарий (P01–P04), загрузить свой JSON того же
   формата или открыть сохранённую выгрузку расчёта. «Изменить начальные условия»: заряд аппарата,
   солнечная мощность, приоритет задания, период недоступности, число каналов связи. Изменённый
   вариант сохраняется как новый сценарий.
2. **Цель и алгоритм.** «Приоритетное обслуживание» или «Коммерческая отдача»; алгоритм
   `reserve` (по умолчанию, секунды на смену), `cpsat-mpc` (максимальный результат, до нескольких
   минут на смену) или `greedy-edf` (простое правило).
3. **Расчёт.** «+1 шаг» (клавиша `1`), «+1 час», «До шага N» — остановка перед нужным шагом,
   «До конца смены». Долгий расчёт идёт в фоне с прогрессом.
4. **Сообщение.** Вкладка «Сообщения» на текущем шаге: недоступность аппаратов или отмена сеансов
   связи (выбор аппаратов и конца интервала), новые задания (конструктор) или JSON. «Оценить
   последствия» — досчитать смену с сообщением и без, не меняя запуск; «Применить» — принять.
   Некорректное или повторное сообщение отклоняется с объяснением, состояние не меняется.
5. **Продолжение.** Расчёт продолжается с фактического состояния: заряд, температура,
   калибровка и прогресс сохраняются. Цель можно сменить на границе шага.
6. **Анализ.** «Обзор» (итоги, прогноз с предупреждениями, журнал алгоритма), «Расписание»
   (диаграмма Ганта, клик — разбор решения), «Аппараты» (графики заряда, температуры,
   калибровки), «Задания» (статус и «почему?»), «Анализ потерь».
7. **Сравнение.** «Ветвь отсюда» или «Рассчитать ветви» — продолжения из одного состояния разными
   стратегиями с выводом, какая лучше для цели; «Сравнить два запуска».
8. **Результат.** «Выгрузка JSON» (формат `cosmo-B-ops-result-1.0`) и «Отчёт» (HTML).
   Воспроизведение выгрузки:

   ```bash
   python model/operations.py --result result.json --output replay.json
   ```

## Что реализовано

| Требование постановки | Как |
|---|---|
| Загрузка и проверка сценария, изменение условий | каталог + загрузка JSON, проверка `validate()` организаторов, `overrides` → новый сценарий с шага 0 |
| Автономное планирование и исполнение | три планировщика; действие на каждый шаг; исполнение библиотекой организаторов |
| Пошаговый и ускоренный расчёт, остановка перед шагом | `advance` по шагам / до шага / до конца, фоновые задачи с прогрессом |
| Три типа сообщений, ручной ввод | `add_jobs`, `satellite_outage`, `close_downlink`; формы в интерфейсе; атомарная проверка |
| Две цели управления, смена цели на границе шага | веса цели в планировщиках; смена пишется в историю и `run_metadata` |
| Сравнение вариантов из одного состояния | ветви (`fork`) с копией состояния и планировщика; сравнение с выводом |
| Анализ и объяснения | расписание, графики, задания, причины потерь отдельно от причин отказа команд, разбор решения, доказательство невыполнимости |
| Сохранение результата | выгрузка JSON с событиями, командами, параметрами и версией алгоритма; HTML-отчёт; загрузка выгрузки обратно |
| Сравнение с простым правилом | `greedy-edf`, одинаковые условия, [эксперименты](docs/EXPERIMENTS.md) |
| Данные разных запусков не смешиваются | изоляция по `X-Client-Id`, независимые запуски и ветви |

## Алгоритм

Два режима. **`reserve`** (по умолчанию) — резервирование «всё или ничего»: задание берётся, только
если вся его работа помещается в окна с учётом связи, каналов, калибровки и заряда; секунды на
смену, все выполнимые приоритетные задания во всех сценариях. **`cpsat-mpc`** — максимальный
результат, оптимизация на скользящем горизонте. Каждый час модельного времени, а
также после сообщения, смены цели или отклонения от плана решается точная задача расписания на
3 часа вперёд (OR-Tools CP-SAT) со всеми ограничениями сразу: окна связи, лимит каналов,
калибровка, заряд. Ключевые решения:

- **заряд в плане — гарантированная нижняя оценка реального**, поэтому план не нарушает резерв —
  ни одной отклонённой команды;
- **задание выполняется целиком или не начинается** — работа не тратится на то, что не успеет;
- **стартовое решение — быстрый план резервирования (`reserve`)**, исполняется лучший из двух,
  поэтому результат не хуже эвристики; на перегрузке (P04), где точная модель не укладывается в
  бюджет, используется резервирование;
- детерминизм: на одной платформе одинаковый вход — одинаковое расписание; любой сохранённый
  расчёт воспроизводится точно по командам.

Подробности — [docs/ALGORITHMS.md](docs/ALGORITHMS.md).

## Результаты

Сравнение с доказанным потолком — LP-релаксацией всей смены, выше которой не может подняться ни
один алгоритм (`make bounds`). «п3» — задания приоритета 3 в срок.

| Сценарий | Цель | Простое правило | `cpsat-mpc` | От потолка |
|---|---|---|---|---|
| P01 | приоритет | 11 · п3 2 · $151 | 11 · п3 2 · $151 | 100% |
| P02 | приоритет | 1146 · п3 312 · $27 106 | **1164 · п3 315 · $27 407** | 100% |
| P02 | выручка | 1131 · п3 298 · $26 906 | **1164 · п3 315 · $27 407** | 100% |
| P03 | приоритет | 1094 · п3 284 · $26 144 | **1162 · п3 315 · $27 387** | 99,8%, п3 100% |
| P03 | выручка | 1085 · п3 281 · $26 039 | **1164 · п3 315 · $27 407** | 100% |
| P04 | приоритет | 6250 · п3 1652 · $155 731 | **6150 · п3 1673 · $185 336** | п3 100%, выручка 97,3% |
| P04 | выручка | 6539 · п3 1282 · $167 065 | **6203 · п3 1387 · $187 154** | выручка 98,1% |

`reserve` (по умолчанию) даёт P02 99,9%, P03 97,5% заданий, P04 — как `cpsat-mpc`; все приоритетные
задания во всех сценариях ([таблица](docs/EXPERIMENTS.md#2-результаты-на-выданных-сценариях-без-сообщений)).
На новых условиях (другое число каналов, размер задачи, отказы, случайные сообщения) результат
такой же — [стресс-проверка](docs/EXPERIMENTS.md#5-стресс-проверка).

44 задания в каждом суточном сценарии невыполнимы при любых действиях — окну не хватает шагов
связи; в P04 работы больше, чем может выполнить группировка. Полный разбор, результаты после
сообщений и стресс-проверка — [docs/EXPERIMENTS.md](docs/EXPERIMENTS.md).

## Дополнительные функции

| Функция | Где | Польза для оператора |
|---|---|---|
| Доказанный потолок и доказательство невыполнимости | «Анализ потерь», «Задания → почему?», `make bounds` | отделяет ограничения задачи от недостатков алгоритма: в P02 с событиями 55 из 56 просрочек невыполнимы при любых действиях |
| Прогноз до конца смены с предупреждениями | «Обзор → Рассчитать прогноз» | заранее видно, какой аппарат уйдёт ниже резерва, у кого истекает калибровка, какие приоритетные задания под угрозой |
| «Что если принять сообщение» | «Сообщения → Оценить последствия» | до применения видно, сколько заданий будет вытеснено и как изменится выручка |
| Ветви стратегий | «Сравнение → Рассчитать ветви» | несколько продолжений из одного состояния с выводом, какое лучше для цели; P04: «приоритет» держит +286 приоритетных заданий ценой 1% выручки |
| Эффект ресурса | «Что если» | стоит ли добавлять канал связи или мощность: в P02 третий канал ничего не даёт — ограничение в окнах связи |
| Журнал алгоритма | «Обзор → Как работал алгоритм» | почему и когда пересчитан план, доказан ли оптимум на горизонте |

## Плюсы и ограничения

Сильные стороны:
- потолок в P01–P03 и 97–98% в P04, все выполнимые задания приоритета 3 во всех сценариях;
- ни одной отклонённой команды, нехватки питания и работы впустую;
- каждое решение и каждая потеря объяснимы, невыполнимость подтверждается расчётом;
- выгрузки воспроизводятся утилитой организаторов, запуски переживают перезапуск сервиса.

Ограничения:
- максимальный результат (`cpsat-mpc`) на сервере с одним ядром считается минуты (P03 — 6,5 мин),
  поэтому по умолчанию выбран быстрый `reserve` (P03: 97,5% вместо 99,8–100% заданий);
- на перегрузке (P04) работает эвристика резервирования, а не точное решение;
- горизонт планирования 3 часа; будущие отказы не прогнозируются — план перестраивается после
  сообщения;
- параметры подобраны на выданных сценариях; проверка на других условиях —
  [стресс-проверка](docs/EXPERIMENTS.md#5-стресс-проверка).

## Компоненты

FastAPI, Uvicorn, Pydantic, OR-Tools (CP-SAT, GLOP), React, Vite. Расчётная модель — `model/`
из комплекта организаторов. Дизайн интерфейса — ArGals666.

Замечание по данным: в описании данных допустимая температура операций указана от 5 °C, в
сценариях `payload_min_c = −5`. Сервис использует значения из сценария; на результаты это не
влияет — температура в данных остаётся в диапазоне 4–36 °C.
