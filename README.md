# Orbit Planner

Веб-сервис автономного планирования работы спутниковой группировки.
КосмоХакатон 2026, кейс «Автономное управление спутниковой группировкой».

Оператор загружает сценарий, выбирает цель управления (приоритетное обслуживание или
коммерческая отдача), запускает расчёт по шагам, вводит сообщения (новые задания,
недоступность аппаратов, отмена сеансов), сравнивает ветви из одного состояния,
разбирает причины потерь и выгружает воспроизводимый результат.

## Запуск

Требования: Python 3.10+, Node.js 20+.

```bash
make install     # venv + npm install
make dev-api     # API на :8000, документация OpenAPI на :8000/docs
make dev-ui      # UI на :5173 (проксирует /api на :8000)
make test        # pytest
```

Один процесс (UI собран и раздаётся FastAPI): `make serve` → http://localhost:8000.
Docker: `docker build -t orbit-planner . && docker run -p 8000:8000 -v orbit-storage:/app/storage orbit-planner`.

## CI/CD и деплой

Конвейер `.github/workflows/ci-cd.yml`:

1. **CI** на каждый пуш и пул-реквест: тесты бэка на Python 3.10 и 3.12, воспроизведение
   сохранённых расчётов утилитой организаторов, проверка типов и сборка фронта, сборка Docker-образа
   и проверка запущенного контейнера.
2. **CD** при пуше в `main`: образ `orbit-planner:<sha>` передаётся на сервер по SSH (`docker save` →
   `docker load`, без реестра), `deploy/deploy.sh` переключает версию, ждёт `/api/health` и при сбое
   возвращает предыдущую. Хранилище запусков — том `orbit-storage`, переживает обновления.
3. **Откат вручную**: Actions → CI/CD → Run workflow → `rollback`.

Сервер: nginx на порту 80 проксирует на `127.0.0.1:8000`; фаервол открыт только для SSH, HTTP, HTTPS;
вход по SSH только по ключу. CI заходит пользователем `deploy`, ключ которого ограничен
принудительной командой `orbit-ci-entry`: загрузить образ, обновить `compose.yml`/`deploy.sh`,
выкатить или откатить — без shell.

Первичная настройка (один раз):

```bash
ssh-keygen -t ed25519 -N "" -C orbit-planner-ci -f ~/.ssh/orbit_deploy
ssh root@HOST "bash -s -- '$(cat ~/.ssh/orbit_deploy.pub)'" < deploy/server-setup.sh
gh secret set DEPLOY_SSH_KEY < ~/.ssh/orbit_deploy
gh variable set DEPLOY_HOST --body HOST
gh variable set DEPLOY_KNOWN_HOSTS --body "$(ssh-keyscan -t ed25519 HOST)"
```

Логи и состояние на сервере:

```bash
ssh root@HOST 'cd /opt/orbit-planner && docker compose -p orbit logs --tail 100 app'
ssh root@HOST 'cat /opt/orbit-planner/.current_tag /opt/orbit-planner/.previous_tag'
```

Переменные окружения: `ORBIT_STORAGE_DIR` (хранилище запусков, по умолчанию `storage/`),
`ORBIT_MAX_RUNS` (запусков в памяти), `ORBIT_TASK_WORKERS` (потоков фоновых задач).

## Принципы

- **Изоляция.** Клиент передаёт заголовок `X-Client-Id` (1–64 символа `[A-Za-z0-9_-]`); запуски
  и сохранённые сценарии разных клиентов не видны друг другу. Без заголовка — клиент `public`.
- **Сохранность.** Каждое изменение запуска пишется на диск (сценарий по хэшу, сообщения, команды).
  После перезапуска сервиса запуск восстанавливается повторением команд — состояние пересчитывается.
- **Временная корректность.** Сообщение применяется только на текущем шаге, до выбора действий;
  выполненные шаги не пересчитываются. Некорректное или повторное сообщение отклоняется целиком,
  состояние не меняется. Планировщик видит только полученные сообщения.
- **Ветви независимы.** `fork` копирует состояние среды, историю и планировщик.
- **Прогнозы не меняют запуск** и помечаются как прогноз: будущие сообщения неизвестны.
- **Изменённые условия — новый эксперимент** с шага 0.
- **Занятый запуск** (идёт фоновый расчёт) отвечает `409` на изменения.

## API

Полная схема — `/docs`. Тяжёлые операции принимают `"background": true` и возвращают задачу (`202`);
её статус и результат — `GET /api/tasks/{id}`.

### Сценарии

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/api/meta` | цели, планировщики, типы сообщений, ключи изменений, сценарии |
| GET | `/api/scenarios` | встроенные и сохранённые сценарии |
| GET | `/api/scenarios/{id}` | состав группировки, модель, задания; `?full=true` — весь JSON |

`overrides`: `initial_soc` `{sid или "*": pct}`, `solar_factor`, `job_priority` `{job_id: 1..3}`,
`failures` `[{satellite_id, start_step, end_step}]`, `downlink_parallel_limit`.

## Причины невыполнения

Причина отказа команды (факт одного шага) и причина срыва задания разделены. Для задания
перебираются все шаги окна, где у допустимого аппарата был контакт, и для каждого определяется,
что помешало. Допустимость по энергии и температуре пересчитывается по правилам модели.

| Причина | Смысл |
|---|---|
| `infeasible_contacts` | доказуемо: шагов со связью в окне меньше, чем работы — неустранимо |
| `busy_other_job` | аппараты работали над другими заданиями |
| `ground_capacity` | оба канала связи с Землёй заняты |
| `calibration_expired` / `calibrating` | калибровка истекла / шла в шаг связи |
| `energy_reserve` / `thermal_limit` | операция нарушила бы резерв заряда / температурный диапазон |
| `satellite_unavailable` | аппарат недоступен |
| `not_scheduled` | условия позволяли, планировщик выбрал другое — недостаток алгоритма |

## Планировщики

| Имя | Описание |
|---|---|
| `cpsat-mpc` (по умолчанию) | оптимизация на скользящем горизонте: точная модель CP-SAT на 36 шагов вперёд, пересчёт каждые 12 шагов, после сообщений и при отклонении от плана; стартовое решение и запасной план — `reserve` |
| `reserve` | резервирование «всё или ничего»: задание берётся, только если вся оставшаяся работа помещается в окно с учётом связи, каналов, калибровки и энергии; порядок — по цели, клетки — наименее востребованные. Около секунды на смену |
| `greedy-edf` | простое правило для сравнения: приоритет → срок (цель «приоритет») или срок → ценность на шаг (цель «выручка»); калибровка за шаг до истечения |

### Метод `cpsat-mpc`

На каждом пересчёте решается задача на горизонт `H` шагов со всеми ограничениями сразу:

- переменные: задание × аппарат × шаг (только допустимые: окно, исполнитель, контакт, доступность),
  калибровка × аппарат × шаг, заряд аппарата на каждом шаге;
- одно действие на аппарат, один исполнитель на задание, не больше `downlink_parallel_limit`
  передач на Землю за шаг;
- работа над заданием разрешена при действующей калибровке (возраст или калибровка за последние
  `calibration_valid_steps` шагов);
- **заряд — гарантированная нижняя оценка реального**: переход модели `min(C, E + min(ηc·b, b/ηd)·dt)`
  с пессимистичным прогнозом нагревателя и зарядки (траектория температуры при ожидании — самая
  холодная) и консервативным округлением; действие требует заряда не ниже резерва в начале и конце
  шага. Если план допустим в модели, он допустим и в реальности — отклонённых команд нет;
- задание со сроком внутри горизонта выполняется целиком или не начинается: работа на
  просроченные задания не тратится;
- цель: «приоритет» — задания приоритета 3 ≫ выручка; «выручка» — выручка ≫ приоритет 3; затем
  частичный прогресс по заданиям за горизонтом, запас заряда в конце горизонта, более ранняя
  работа (оставляет место срочным заявкам), меньше калибровок.

Решатель стартует с плана `reserve` (он допустим в модели точно — общая целочисленная арифметика
энергии), поэтому результат не хуже эвристики. Если модель больше `max_variables` (перегрузка
P04), используется план резервирования. Детерминизм: один поток, фиксированное зерно,
детерминированный лимит времени. Журнал пересчётов с причиной, статусом и разрывом с границей —
`GET /api/runs/{id}/planner` и вкладка «Обзор».

Параметры: `horizon` (36), `replan_every` (12), `time_limit` (3, детерминированные единицы),
`terminal_soc_pct` (55), `partial_credit` (0.8), `max_candidates` (0 — без отсева),
`max_variables` (15000), `energy_margin_wh` (0.3), `seed` (0).

### Верхние границы

`python -m experiments.upper_bound` решает LP-релаксацию всей смены: те же ограничения назначений,
калибровка снята, энергия в оптимистичной форме (нагреватель выключен, зарядка всегда разрешена,
без округлений). Ослабление ограничений только поднимает оптимум, поэтому это доказанный потолок
для любого алгоритма (для запусков без нехватки питания). Проценты в таблице ниже — от него.

Новый планировщик — класс с `name`, `version`, `params()`, `plan(session, goal)`, добавленный в
`PLANNERS`. Он видит только текущее состояние и полученные сообщения. Экземпляр копируется при
ветвлении; после восстановления с диска создаётся заново и может восстановить внутреннее
состояние в необязательном `restore(session)`.

- **P01–P03: доказанный максимум** (P03 «приоритет» — на одно задание ниже потолка). 44 просрочки

  Где важна скорость, `reserve` почти не уступает (P03: 97,5% заданий, все приоритетные).

## Использованные компоненты

FastAPI, Uvicorn, Pydantic, OR-Tools (CP-SAT, GLOP), React, Vite. Расчётная модель — `model/` из комплекта организаторов.
Платные сервисы и внешние модели не требуются.
